# Decisions made during the build

One line each: what was decided, and why, when the plan didn't cover it.

- `LLMError` lives in `squad/llm.py` from Task 0 so `tests/fakes.py` can import it; Task 4 adds `LLM` to the same file.
- WhatsApp pairing is skipped for now (user choice 2026-10-25): `wa-voice` is built and tested, nudges use DMs until paired.
- Track 3 submission is held until the user records the demo video.

## Wave 1 (builders' choices)
- T3: transit_tip on Rides is empty exactly when transit_ids is empty: if transit_ids is empty, every rider already has a seat, so the plan's two conditions are the same check.
- T3: A building code is a 2-6 letter code in brackets at the end of the stripped location, matched case-insensitively with the regex \([a-z]{2,6}\)$, so 'Coor Hall 174 (COOR)' counts as Tempe.
- T3: ' mu ' is matched against the lowercased location padded with a space on each side. That means 'MU' still matches at the start or end of the string, and words that merely contain 'mu', like 'museum', do not.
- T3: Members with seats <= 0 are riders. A driver's car takes the next riders in name order up to that driver's seats; anyone left over goes to transit_ids.

- T7: persona_busy converts week_of to tz, takes that local date's Monday, and builds tz-aware blocks with datetime.combine(date, time(h), tz); members without blocks (Jordan, Priya, real members) get [].
- T7: persona_busy keeps busy times in a private _BUSY table keyed by member id (days after Monday, start hour, end hour) instead of filling Member.demo_busy, because the plan says the blocks are relative to week_of.
- T7: INTRO_LINES and DEMO_VOTES are keyed by the short name (maya/jordan/priya/leo), not 'demo:<name>', following the plan's wording.
- T2: slot_covers: converts to the local tz and checks that the start's weekday is in the slot, that the start is at or after the slot's start hour on that day, and that the end is at or before day-midnight + end_hour (so end hour 24 means midnight of that day). An unknown slot key returns False.
- T2: is_free with busy: a block overlaps if b.start < end and b.end > start - TRAVEL_MIN, so a block that touches the window edge exactly does not count.

- T2: Learned filters with a malformed value (int/float ValueError or a bad regex) are treated as not matching instead of raising, because their values come from parsed chat replies.

- T9: Checked the google-genai 2.33.0 API names in the installed source: client.aio.live.connect(model, config), session.send_realtime_input(audio=Blob), session.receive() (yields messages until one turn is complete, so the bridge calls it in a loop and stops when it yields nothing), LiveServerMessage.data and .tool_call.function_calls, session.send_tool_response(function_responses=FunctionResponse(id, name, response)). - T9: The 90 s limit and the 3 s goodbye wait are module constants CALL_LIMIT_S and GOODBYE_S, so tests can patch them. The 90 s timer starts after POST /call succeeds and covers the WebSocket, the Gemini connect and both audio pumps.
- T9: answered=True is set by the sidecar's {"event":"answered"} or by a valid record_answer call. The call hangs up GOODBYE_S seconds after the first turn_complete that arrives once an answer is recorded. seconds runs from Gemini setup to the end, rounded to 0.1.
- T9: nudge_call never raises. A non-200 from /call or any exception gives CallOutcome(answered=False), and only the exception type name is logged, so no secret can reach the log. If an audio pump fails, the answer already recorded is kept. {"cmd":"hangup"} is always sent in finally.
- T9: ws_connect is a callable(url) whose result is awaited to get the WebSocket. By default it is aiohttp ClientSession.ws_connect.
- T9: 'when' is formatted as plan.event.start in settings.tz with '%A %-I:%M %p'. 'going' is the names joined with ', ', or 'nobody yet' when the list is empty.
- T9: The catch-all except is marked noqa: BLE001 on purpose, because a failed nudge must not crash a flow (Review Focus 3).

- T8: whatsapp-rust features copied from examples/voip-cli/Cargo.toml: sqlite-storage, tokio-transport, ureq-client, tokio-native, voip-relay-native, plus voip-mlow (the example's default codec). wacore uses features ["voip"], also as in the example. I left out the example's optional voip-opus (voip-encoded + voip-libopus) so the build doesn't need libopus.
- T8: Cargo.lock is committed so the build stays pinned to whatsapp-rust main at 9b9fdb7e (wa-voice is a binary crate). The task's file list didn't name Cargo.lock, but cargo creates it and the build needs it to be reproducible.
- T8: Calls use client.voip().call(&jid).audio(mic_rx, speaker_tx).start() with MLOW, the same as the example. The newest whatsapp-rust also has .audio_opus(..), and its docs say MLOW can drop the first ~1 s of what the callee says. If the live check loses short answers like 'yeah', switch that one call to audio_opus and add the voip-libopus feature.
- T8: The 'answered' event is sent when CallHandle::media_connected() turns true. This is checked every 200 ms. For an outgoing call it means the callee accepted and the media keys are installed.
- T8: 'ended' is sent when CallHandle::wait_ended() resolves. The reason is the first one recorded: 'hangup' (the client sent {"cmd":"hangup"}), 'bridge disconnected' (the WebSocket closed), 'max duration', or the Debug text of CallEvent::Closed (for example RelayDisconnected). If none was recorded it is 'ended'.
- T8: Audio from the client is cut into 960-sample frames (audio::bytes_to_frames) and goes into an unbounded queue. A pacer task sends one frame every 60 ms into a bounded(8) mic channel, and sends silence when the queue is empty, like the example's continuous microphone. This means bursty Gemini audio plays at real-time speed. The callee's audio goes into a bounded(64) speaker channel; frames are dropped when nobody reads it, which is the engine's loss-tolerant default.
- T8: POST /call checks in this order: 400 bad phone, 409 busy, 503 not connected (client.is_session_ready()). If start() fails it returns 502, which the contract doesn't cover; the Python side treats any non-200 as unanswered. A JSON body that doesn't parse gets axum's default 4xx.
- T8: Only one call at a time: a tokio Mutex is held across start(). GET /status uses try_lock, so busy is true while a call is being placed.
- T8: Safety nets: a call is terminated after 150 s even if nobody hangs up, and closing the WebSocket also terminates the call. Either way the sidecar can't stay stuck at busy/409.
- T8: 'paired' is an AtomicBool. It is set true on the Connected or PairSuccess events and false on LoggedOut, so after a restart it reads false for the few seconds before reconnecting. The QR string is logged and written to data/wa-qr.txt from on_qr_code, and the file is deleted on Connected or PairSuccess. The paths data/wa-voice.db and data/wa-qr.txt are relative to wa-voice/ and are already gitignored by the existing 'data/' pattern.
- T8: JID = <digits>@s.whatsapp.net, parsed as Jid. Resolving a LID (the plan's 'must be LID' fallback) is not implemented, because it can only be checked on a live call.
- T8: I added two small unit tests in main.rs (phone_validation and hangup_command) alongside the two required audio.rs tests (chunks_and_keeps_remainder and roundtrip_little_endian).
- T9: Goodbye fix: model_to_callee now ends only on a turn_complete after model audio has arrived following send_tool_response (flags `responded` and `goodbye`). The silent tool-call turn's turn_complete is skipped, and audio keeps going to the sidecar until the goodbye turn completes; then the bridge sleeps GOODBYE_S. I keyed on 'audio after the tool response' rather than 'the second turn_complete' because it holds whether the tool call comes with or without audio in its turn. If the model never speaks a goodbye, the call ends when the callee sends 'ended' or at the 90 s limit.
- T9: Hangup fix: I added a `_hangup(ws)` helper that does nothing if `ws.closed`. _bridge calls it in its finally, right after the pumps are cancelled and while still inside `async with live.connect(...)`, so the hangup no longer waits for the slow Live close (about 10 s). nudge_call's finally still calls `_hangup` as the 'always send hangup' fallback (connect errors, timeout before the session opens); it does nothing if the socket is already closed.
- T9: CallOutcome.seconds is now measured at hangup time (`ended`), not after the Live session close. If the timeout fires before the session opens, it is measured at return as before.
- T9: Test: test_nudge_call_records_answer now uses the real message order [[audio, tool_call, turn_complete], [goodbye audio, turn_complete]]. It asserts that both audio chunks (2*3200 bytes) reached the sidecar before it saw the hangup. FakeGenai takes an optional async on_close hook called from __aexit__. The test uses it to assert the sidecar got the hangup before the Live session close (the hook polls up to 1 s, because aiohttp ws.close() returns before the server reads the frame). The new test failed against the old bridge, and failed again with the in-session hangup line removed. It passes with the fix.
- T8: Fixed in code rather than in the docs: place_call now takes axum::body::Bytes and parses CallRequest with serde_json::from_slice. A parse error returns 400 {"error": "bad json: ..."}. A missing Content-Type header is accepted, so the plan's `curl -XPOST 127.0.0.1:8091/call -d '{"phone":...}'` works unchanged, and so does the aiohttp json= bridge call.
- T8: README and the plan's live-check command are unchanged because they are now correct as written.

Try /squad demo in a server channel where I can manage webhooks 🙂" instead of the success copy, because no intros were posted.
